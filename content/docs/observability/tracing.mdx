Every request handled by Kwiva produces a tree of trace spans automatically. The tracing runtime wraps the framework's own machinery — middleware, validation, controllers, model queries, cache lookups, and responses — so you get a full picture of where time goes without adding a single span by hand.

## One Tree per Request

A typical request produces a shape like this:

```text title="one-tree-per-request.txt"
http GET /api/posts (server)
 ├─ middleware.request-id
 ├─ middleware.session
 ├─ middleware.tenant
 ├─ validation (route schema)
 ├─ controller posts.list
 │   └─ model posts.query (sql + params normalized)
 ├─ cache.get posts:...
 └─ http.response (status, size)
```

Each span nests inside the one before it. The `controller posts.list` span, for instance, contains every model query it performed, and the query spans carry normalized SQL and redacted parameters — never raw values. The tree is the request's actual cost accounting, in order.

## What Gets Spans

Spans are not limited to HTTP. Every unit of work the framework owns is traced on the same runtime:

| Work | Spans produced |
|---|---|
| Requests | Middleware chain, validation, controller, queries, cache, response |
| Jobs | Dispatch to run, including retry attempts |
| Tasks | Scheduled task execution |
| Events | Emit to listener for every registered listener |
| MCP tool calls | Tool invocation and input validation |
| SSR renders | Loader, render, and stream stages |

Breadth like this is what makes tracing useful: a user reporting a slow page, a job that deadlocks, or an event handler that drags can all be traced through the same runtime and queried the same way.

## Reading a Tree

The tree's shape is its explanation. A request that spends 900 milliseconds total with 800 of them inside `model posts.query` is a query problem, not a routing problem — the span tree says which layer owns the time. Retries within a job render as repeated attempt spans under the same job root, so a job that succeeds on the third try tells a complete story instead of a single ambiguous duration.

## Model Query Spans

Every query builder call is traced with two attributes that matter in production:

- Normalized SQL — the query template, not the interpolated values
- Redacted parameters — bound values are scrubbed before they reach a span

This is a deliberate PII and secret-safety decision. Trace data stays useful for debugging while never shipping full-text values or credentials to your collector. Query spans carry the model and operation as well, which makes them directly joinable to the metric series (`model_queries_total`, `model_query_duration`) on [Metrics](/docs/observability/metrics).

## Custom Spans

When you need a span for work that lives outside the framework boundaries, the same tracing runtime is exported for app code:

```ts title="custom-spans.ts"
import { trace } from '@kwiva/core'

await trace('billing.recalc', async (span) => {
  span.setAttr('tenantId', tenant.id)
  // ... your logic
})
```

Custom spans nest inside the current request or job span automatically, so they join the existing tree instead of floating in isolation.

> [!TIP]
> Wrap anything long-running or externally observable — gateway calls, report generation, cache warming — in `trace`. A span that exists costs nothing when no exporter is configured, and it pays off the first time the operation is slow and you have to explain where the time went.

## Distributed Context

Correlation IDs are the glue between tracing and logging. Within any scope, every log line carries `traceId` and `spanId` alongside `requestId`, and context propagates across framework hops — a request that dispatches a job, an event that triggers a listener, a page that streams a query all stay in one trace. To walk a failing request end to end:

1. Get the `requestId` from the error report or the `x-request-id` header.
2. Pull every log line with that `requestId` from your log store.
3. Enlarge to `traceId` to include spans from background workers and event listeners.

The trace context follows the OpenTelemetry contract and the W3C trace context propagation standard, so a trace that hops a service boundary — outbound to a gateway, a worker, or a hosted render — carries the same identifiers to whatever honors the standard.

## Sampling

Trace data is collected at a configurable rate, applied at the root span so every descendant of a sampled request is exported as a complete tree — you never get a half-tree from mixed sampling decisions.

- Development samples everything (`1.0`) so the dev overlay and local debugging are complete.
- Production guidance is `0.1` — enough to detect latency regressions and failure spikes while keeping export volume manageable.
- Errors are always sampled: a failing request is the one you want to see, independent of the roll of the dice.

Sampling affects collection, not metrics — metric series are aggregated and effectively always-on regardless of the trace sample rate.

## Health Endpoints

Two health endpoints ship with every application:

- `/healthz` — liveness. Returns OK when the process is up.
- `/readyz` — readiness. Pings the database, the queue, and storage, and returns OK only when all configured dependencies respond.

Readiness checks are the correct target for orchestrators and load balancers; liveness is the correct target for process supervisors. Load balancers that add an instance before it is ready — or keep one that has lost its queue — get a definitive signal instead of timing out.

## Configuration

Telemetry configuration lives in `src/config/telemetry.ts`:

```ts title="configuration.ts"
export default defineConfig('telemetry', {
  defaults: {
    sampleRate: 1.0,          // dev 1.0; production guidance 0.1
    exporters: { otlp: { endpoint: 'http://collector:4318' } },
    logs: { level: 'info', pretty: true },   // dev
    metrics: { interval: 10_000 },
  },
})
```

Two settings matter most in production:

- **`sampleRate`** — trace every request in development (`1.0`) and a fraction of traffic in production (guidance `0.1`). Sampling is applied at the root span so every descendant of a sampled request is exported as a complete tree.
- **`exporters`** — data is exported over HTTP to a collector-compatible endpoint. With no exporters configured, tracing degrades to a no-op with negligible overhead.

Exporter failures never break the app: errors are swallowed and counted, which is the framework's standing principle that observability must not become a dependency of uptime.
