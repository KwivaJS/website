Creating a Kwiva project is a single scaffold command. The CLI generates the complete application skeleton — configuration entry, conventional directories, a working home page, and a testable development server — so your first hour is spent building features, not wiring infrastructure.

## Quick Start

```bash
bun create kwiva my-app
```

This is equivalent to `kwiva new my-app`. The scaffold command:

1. Creates the `my-app/` directory and `package.json`
2. Installs dependencies and generates `kwiva.config.ts` and `tsconfig.json`
3. Creates the conventional `src/` layout (models, http, config, database, ui)
4. Scaffolds a working home page and the application kernel in `src/bootstrap/app.ts`
5. Generates `.env.example` from the variables your configuration declares

When it finishes, you can verify the install immediately:

```bash
cd my-app
bun run dev
```

Open `http://localhost:3000` to see the home page.

## What Gets Scaffolded

A default `fullstack` project includes this layout:

```
my-app/
├─ kwiva.config.ts            # defineConfig — the app entry (loads src/config)
├─ package.json
├─ tsconfig.json
├─ .env / .env.local / .env.example
├─ public/                    # static assets served as-is (favicon, robots.txt)
├─ storage/                   # runtime data: sqlite db, uploads, logs, cache
├─ tests/                     # unit, integration, and e2e tests
└─ src/
   ├─ bootstrap/
   │  └─ app.ts               # defineApp — the application kernel
   ├─ app/
   │  ├─ models/              # defineModel — empty, ready for models
   │  ├─ http/
   │  │  ├─ controllers/      # defineController — empty, ready for controllers
   │  │  ├─ middleware/       # defineMiddleware
   │  │  └─ auth.ts           # defineAuth (generated by kwiva make:auth)
   │  ├─ services/            # defineService — business logic
   │  ├─ jobs/                # defineJob — background jobs
   │  ├─ events/              # defineEvent — domain events
   │  ├─ policies/            # definePolicy — authorization
   │  ├─ tasks/               # defineTask — background tasks
   │  └─ console/             # defineCommand — app-defined CLI commands
   ├─ routes/                 # explicit registration + route rules
   ├─ config/                 # ALL configuration lives here (defineConfig)
   ├─ database/
   │  ├─ migrations/          # generated, editable SQL-step files
   │  ├─ seeders/             # defineSeeder
   │  └─ factories.ts         # model factories
   └─ ui/
      ├─ pages/               # definePage — file-based routing
      │  ├─ __root.tsx        # root layout
      │  └─ index.tsx         # home page
      ├─ components/          # shared components
      ├─ hooks/               # custom hooks
      └─ styles/              # global css entry
```

The `src/.kwiva/` directory is also created at first boot: it holds generated artifacts (the route manifest, the model IR, and ambient types) and is **never hand-edited or committed**.

## Choosing a Mode

Every project is scaffolded in one of five modes. The mode controls which framework surfaces are included and the default deployment preset.

```bash
bun create kwiva my-app --mode=<mode>
```

### `fullstack` — SSR + API (default)

The complete application: server-rendered pages, an HTTP API, background work, auth, and realtime in one codebase. The default target for most products and the mode the tutorials assume.

```bash
bun create kwiva saas --mode=fullstack
```

### `api+spa` — API server + single-page app

A backend with no SSR renderer; the frontend is a client-rendered SPA shell. Use it when your UI is a separate concern (for example a mobile app consuming the same API, or a team that owns the frontend independently). You can scaffold without any UI at all:

```bash
bun create kwiva acme-api --mode=api+spa --no-ui
```

### `static` — static site generation

The whole app prerenders to static HTML at build time. No server is required at runtime, and model data can be baked in at build time (for example SQLite content or seeded documents). Ideal for documentation, marketing sites, and blogs.

### `standalone` — single-binary output

An API-only profile compiled into a single zero-dependency executable with `kwiva build --binary`. Ideal for internal tooling, microservices, and background workers you want to copy onto a host as one file.

### `edge` — edge runtimes

Built for edge platforms with an edge-safe constraint set: static-importable handlers, no long-lived in-memory state, storage through the framework's storage API, and platform web APIs instead of runtime-exclusive ones. The default preset is `cloudflare_worker`.

### Mode Variations

| Mode | What's omitted / changed | Notes |
|---|---|---|
| `api+spa` | `src/ui/pages` (optional) | SSR renderer off; SPA shell served |
| `static` | `src/app/http`, `src/app/jobs`, and friends | Prerendered pages only |
| `standalone` | nothing | Single-binary output |
| `edge` | same tree, edge-safe constraints | Deploy preset differs |

> [!NOTE]
> Modes are profiles, not separate frameworks. A `static` site and a `fullstack` SaaS use the same packages, the same config model, and the same model definitions — only the enabled surfaces and the output differ.

### What Each Mode Ships

| Directory / concern | `fullstack` | `api+spa` | `static` | `standalone` | `edge` |
|---|---|---|---|---|---|
| `src/bootstrap/app.ts` | included | included | included | included | included |
| `src/app/models/` | included | included | included | included | included |
| `src/config/` | included | included | included | included | included |
| `src/app/http/` | included | included | minus controllers/jobs | included | included |
| `src/ui/pages/` | included | optional (no SSR) | included | — | included |
| Deploy default | node server | node server + client | static | binary | edge worker |

The config folder and the model layer — the parts that carry your application's meaning — are identical in every mode; the variations are confined to which surfaces are enabled and how the build is emitted. That is what makes migrating a project between modes low-risk: you add or remove directories, keep your models, and rebuild.

## Verify the Install

Beyond starting the dev server, two quick commands confirm the scaffold is healthy:

```bash
bun run check     # format + lint + typecheck in one pass
bun run test      # the empty-but-wired test suite passes
```

`kwiva check` enforces the project conventions (lowercase filenames, `@kwiva/*`-only imports, no engine imports) with the lint gates, so it's the earliest signal that everything is set up correctly.
