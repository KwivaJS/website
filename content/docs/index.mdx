## Overview

Kwiva is the **batteries-included TypeScript application framework**. Instead of assembling a dozen unrelated libraries — a router here, a data layer there, a separate auth kit, a build tool, a generated client, and yet another admin UI — your application talks to one coherent framework: a framework-owned `@kwiva/*` API surface, a single configuration model, one CLI, and a Rust-speed toolchain for instant feedback.

You write plain TypeScript. App code imports only from `@kwiva/*` packages. Every construct you declare — a model, a controller, a page, a job, an event, a mail — is a `defineX` factory. Reading Kwiva app code should feel like reading a description of the product: models describe the data, controllers describe the HTTP surface, pages describe the UI, and the framework derives the rest.

### The problem it solves

A serious TypeScript application today usually means gluing unrelated libraries together. Each library ships its own conventions, its own configuration, its own failure modes, and its own upgrade cadence. Types stop at library boundaries. Configuration spreads across four formats. "Shipping" means re-learning integration details for every new element of the stack. The result is a fragile house of cards — a pile of parts that only coincidentally behaves like an application.

### The solution

Kwiva collapses that stack into a single, coherent framework:

```plaintext title="the-solution.txt"
One project. One configuration model. One CLI. One defineX language.
```

- **Models** derive the entire data layer — database schema, migrations, seeders, REST API routes, the typed RPC client, OpenAPI, and MCP tools
- **Controllers** define HTTP endpoints with typed context, per-route validation, lifecycle hooks, and policy checks
- **Pages** render with streaming SSR, typed loaders, and full-stack type safety from database to browser
- **Auth, authorization, tenancy, queues, realtime, and observability** are built in, not bolted on

## Why Kwiva

Kwiva is organized around four design pillars.

| Pillar | What it means |
|---|---|
| **One defineX grammar** | Every app construct is a `defineX` factory. Models are the single source of truth and derive the whole stack. Plain, serializable definitions — no decorators, no classes, no config sprawl. |
| **Developer experience** | CLI-first generators for everything, a typed config folder with sensible defaults, auto-discovery over manual registration, and friendly errors (did-you-mean suggestions, field-mapped validation, request correlation). |
| **Production-grade out of the box** | Stateless by construction (externalized state), tenancy-first data access, queues and tasks for background scale, edge presets, and one codebase that deploys anywhere. |
| **Extensible without breaking the grammar** | The same grammar declares controllers, pages, jobs, policies, auth, storage, search, realtime — and engines stay sealed behind the framework, never imported by app code. |

## Architecture at a Glance

Kwiva holds one core architectural rule:

```plaintext title="architecture-at-a-glance.txt"
Application (src/) — models, http, pages, jobs, events, config
  ↓  writes defineX(...) only · imports only @kwiva/*
Framework API surface (@kwiva/* — the packages)
  ↓
Sealed engines (framework-owned internals — never imported by app code)
  ↓
Runtime (Bun · Node · serverless · containers · edge) via presets
```

The application depends only on the framework. The framework owns the sealed engines and the Rust-speed toolchain. Whatever preset an application deploys to, it sees the same framework API surface; the differences between runtimes stay inside the engine layer.

### One Definition Multiplies the Stack

A single model definition feeds an intermediate representation (the model IR) from which the rest of the stack is derived — so there is no drift between your types, your API, and your database:

```plaintext title="one-definition-multiplies-the-stack.txt"
src/app/models/*.ts ──► model IR
  ├─► database schema + migrations + seeders
  ├─► typed REST API routes (list / get / create / update / delete)
  ├─► typed RPC client SDK (@kwiva/client)
  ├─► OpenAPI 3.1 spec (/openapi.json)
  ├─► MCP tools (when opted in, policy-checked)
  └─► migrations, seeders, factories, verified by the test suite
```

## The defineX Ecosystem

Every app-facing construct in Kwiva is a `defineX` factory — one consistent convention across the whole framework. Learn one, learn them all.

| Package | Role |
|---|---|
| `@kwiva/core` | Application kernel: `defineApp`, `defineConfig`, `loadConfig`, typed context/ALS, errors, `defineService`, model IR helpers, cache, KV, store contracts |
| `@kwiva/data` | Models, field DSL, relations, query builder, transactions, migrations, seeders, factories, search ops |
| `@kwiva/http` | Controllers, contracts, routes, middleware, server/pipeline, SSE/streams, WebSockets, OpenAPI, caching |
| `@kwiva/ui` | Pages, layouts, routing, SSR/streaming/hydration, islands, navigation, SEO helpers, `./server` |
| `@kwiva/client` | Typed RPC client (Eden + TanStack Query), reads/mutations/infinite/form/upload hooks, cache persistence, token refresh, WS |
| `@kwiva/auth` | `defineAuth` providers, sessions, identity flows, policies/gates/abilities, controllers, middleware |
| `@kwiva/jobs` | Jobs, queues, workers, middleware, unique jobs, outbox, priorities, failed-job registry, tasks, cron scheduler, observability |
| `@kwiva/events` | Events, listeners, broadcast, subscribers, config, testing fakes |
| `@kwiva/mail` | `defineMail`, templates (markdown + string + components), transports (memory/console/SMTP/Resend) |
| `@kwiva/mcp` | MCP v2: config, tool generation (model + controller), custom tools, HTTP fetch + stdio server, auth |
| `@kwiva/storage` | Disks, storage API, uploads, signed URLs, assets, tenant scoping, fakes |
| `@kwiva/search` | Config validation, Postgres FTS, federated search, `reindexSearch` |
| `@kwiva/testing` | `withApp`, `createTestClient`, shared boot seam, DB lifecycle helpers, fakes |
| `@kwiva/cli` | The `kwiva` binary, generators, migrations, db commands, app commands, platform commands |

Plus sealed engine packages (`@kwiva/auth-better-auth`, `@kwiva/jobs-pg-boss`, `@kwiva/mail-resend`, `@kwiva/mail-smtp`, `@kwiva/store-redis`) behind the framework API.

## What you get out of the box

- One model definition that derives: database schema + migrations + seeders, the REST API, the typed RPC client, OpenAPI, MCP tools, and audit trails
- Typed validation at every boundary (field DSL + Standard Schema + contracts), with field-mapped error shapes
- Built-in auth (sessions, providers, identity flows), authorization (policies, gates, abilities), and tenancy-first data access
- Streaming SSR with islands and typed navigation — not bolt-ons, but wired into pages
- Queues and jobs with middleware, retries, batches, and lifecycle observability
- A CLI that generates the whole tree: scaffolding, controllers, migrations, seeders, tests, routes
- A shared, typed config folder per environment with validation

## When to use Kwiva

- Teams building one app on one codebase, full-stack or backend-heavy
- Products that need typed contracts, auth, tenancy, and background work without assembling a dozen libraries
- Products that want a boring, verifiable stack — types and database never drift apart

## When not to use Kwiva

- Teams already happy with their assembled stack of libraries
- Projects that need a visual drag-drop CMS or hosted cloud experience (out of scope for the framework)
- Non-TypeScript applications

## FAQ

### What is Kwiva's relationship with Bun?

Bun is the primary runtime (`engines: bun >= 1.4.0`) and the native execution environment for development — fast startup, isolated module loading, and a fast transpiler-based toolchain. It is a runtime choice, not a framework identity: Node and serverless/container targets stay compatible through presets, and the framework API surface is the same on every target.

### Is Kwiva a framework or a library?

A framework: it owns the application-facing surface, the lifecycle, and the conventions. Applications write `src/app/**` constructs with `defineX` factories and consume `@kwiva/*` — they never import an engine.

### Is the framework versioned?

The docs mirror the current implementation: packages are at `@kwiva/*` `0.2.0`, tracking the `main` branch of the Kwiva framework repo (no git tags yet). See [Versioning & Compatibility](/reference/versioning).

### Studio, addons, and cloud

Not documented on this site — they are roadmap items on the framework side (see `docs/features/studio.md` in the framework repo). This site tracks the shipped product.

```bash title="terminal"
bun run dev        # kwiva dev — scaffolded app on :3000
```
