`@kwiva/client` is the typed RPC client for your application. It is scaffolded once as `src/client.ts` and derives its full shape from this app's controllers and models at the type level — the route manifest and model IR flow into ambient types under `src/.kwiva/types`, so there is no codegen step and no drift between the server contract and the client.

```ts
import { createClient } from '@kwiva/client'

export const client = createClient()
```

## createClient

`createClient` builds the typed client for the current app.

```ts
const client = createClient()
const apiClient = createClient({ baseUrl: '/api' })
```

| Option | Type | Description |
|---|---|---|
| `baseUrl` | `string` | API base the browser client targets when it cannot run in-process |

| Behavior | Description |
|---|---|
| Server-side | Calls run in-process (no network) and dedupe per request |
| Browser | Calls the same-origin API with session cookies flowing automatically |
| Types | End-to-end: model → route → client, resolved from the manifest and model IR |

## Model Endpoints

Each model generates exactly five deterministic routes — `list`, `get`, `create`, `update`, `delete` — plus any custom controller actions. The client mirrors them under the model's resource name.

```ts
const { data, total } = await client.users.list({ where: { role: 'admin' }, page: 1 })
const user = await client.users.get('usr_01h2x8kq9f4m3p6t7y2wv0ba')
const created = await client.users.create({ name: 'Ada L.', role: 'admin' })
const updated = await client.users.update('usr_01h2x8kq9f4m3p6t7y2wv0ba', { name: 'Ada L.' })
await client.users.delete('usr_01h2x8kq9f4m3p6t7y2wv0ba')
```

| Method | Signature (resolved from model IR) | Description |
|---|---|---|
| `list` | `(input?: ListInput) => Promise<{ data: Model[]; total: number }>` | Filtered, paginated listing |
| `get` | `(id) => Promise<{ data: Model } \| { error: ApiError }>` | Single record by id |
| `create` | `(input) => Promise<{ data: Model } \| { error: ApiError }>` | Create with validated fields |
| `update` | `(id, patch) => Promise<{ data: Model } \| { error: ApiError }>` | Partial update by id |
| `delete` | `(id) => Promise<...>` | Delete by id; soft-deletes when the model enables them |

List input is typed from the model: `where` filters match queryable fields, `page` drives offset pagination, and `orderBy` accepts sortable columns. The exact member names follow your model definitions — every input and resolved value is inferred, not annotated.

Errors are part of the resolved type: calls return a discriminated union of the success envelope and `{ error: ApiError }`, so narrowing an error is a type-level operation.

```ts
const result = await client.posts.get(id)

if (result.error) {
  console.log(result.error.code, result.error.message)
  return
}

console.log(result.data.title)
```

## Custom Controller Actions

Actions declared on controllers become methods alongside the generated model endpoints. `defineController` bodies, params, and schemas shape the client, so a route handler surfaces as a typed callable.

```ts
await client.posts.publish('pst_01h2x8kq9f4m3p6t7y2wv0ba')
```

Path params, bodies, and query arguments of the action are typed from the controller route's schemas, and the action returns the same envelope-and-error union as model endpoints.

## Typed Errors

Failures across every call resolve to a typed error rather than an untyped throw:

| Field | Type | Description |
|---|---|---|
| `code` | `string` | Stable machine-readable error code |
| `message` | `string` | Human-readable message |
| `issues` | array (optional) | Validation issues when input failed validation |

```ts
const result = await client.users.create({ name: '' })

if (result.error) {
  if (result.error.issues) {
    return result.error.issues
  }
  return result.error.message
}
```

See [Errors](/docs/http/errors) for the server-side contract that produces these responses.

## Subscriptions

`client.stream` opens a typed subscription on a resource or channel and returns an async iterable of typed events. WebSocket is the primary transport; when WebSocket is unavailable the client transparently falls back to SSE (v1.x).

```ts
const stream = client.chat.stream({ roomId })

for await (const event of stream) {
  console.log(event)
}
```

Server-side, events are pushed to the channel via the channel API and broadcasting. See [Channels](/docs/realtime/channels) and [Events & Broadcasting](/docs/realtime/events).

## SSR-Safe Behavior

The same `client` module runs on the server and in the browser without special-casing:

- During SSR, calls execute **in-process** — no network hop — and dedupe within a request.
- Loaders use the typed client directly; their results serialize into the page and rehydrate into the data-hook cache on the client, so server and browser agree without a second fetch.
- On the browser, calls go to the same-origin API and resolve into the same cache.

This is what lets page loaders, navigation preloads, and data hooks share one cache. See [Loaders & Data](/docs/frontend/loaders) and [Hydration](/docs/rendering/hydration).

## Sessions & CSRF

The client is session-aware by default:

- Session cookies flow automatically on every browser request; nothing is stored or attached by hand.
- The CSRF token is handled by the provider that mounts the client — in an `@kwiva/react` app, `Providers` handles the client-side token wiring.
- In-process (SSR and test) calls carry the request session directly and bypass browser CSRF concerns.

See [Sessions](/docs/auth/sessions) and [Protecting Routes](/docs/auth/protecting-routes).

## createTestClient

`createTestClient` (from `@kwiva/testing`) returns the same typed client bound to a real app instance, running in-process with no network. It is typically used inside the `withApp` harness, which boots the app, migrates, and seeds per test.

```ts
import { withApp, createTestClient } from '@kwiva/testing'

test('posts CRUD', withApp(async (app) => {
  const client = createTestClient(app)

  const created = await client.posts.create({ title: 'First' })
  const { data, total } = await client.posts.list({ where: { title: 'First' } })
}))
```

| Option | Description |
|---|---|
| `tenant` | Runs the client against a specific tenant for tenancy-scoped tests |

The test client is fully typed, so type expectations from `@kwiva/client` hold in tests:

```ts
expectTypeOf(client.posts.list({})).resolves.toMatchTypeOf<{ data: Post[]; total: number }>()
expectTypeOf(client.users.get('x')).resolves.toMatchTypeOf<{ data: User } | { error: ApiError }>()
```

See [API Testing](/docs/testing/api-testing) and [Integration Testing](/docs/testing/integration-testing).
