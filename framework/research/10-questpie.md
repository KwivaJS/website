# Research — Questpie (as Architectural Reference)

**Source**: questpie.com (project), live research 2026-09-08
**Relevance**: **Reference only** (ADR-0004, ADR-0016) — the one-schema model pattern. Kwiva borrows the **architectural ideas** and reimplements everything independently, with **zero runtime dependency** on Questpie.

## What Questpie Is

Questpie (questpie.com) is an MIT, TypeScript+Postgres, Bun-first **one-schema web data framework**. You declare your entire data model in one TypeScript schema; Questpie derives:

- A typed REST API (5 routes per collection)
- A typed client SDK
- A generated admin UI
- Job infrastructure
- Optional MCP connector + OpenAPI

## The Idea We Borrow (the "one-schema" principle)

> Declare the data model **once**; derive every consumer typing from that single source of truth so API, client, admin, and jobs can never drift.

```ts
// Questpie's shape (reference only — NOT a Kwiva dependency)
import { collection } from '@questpie/core'
export const news = collection('news').fields((f) => ({
  title: f.string(),
  body: f.text(),
  publishedAt: f.optional(f.date()),
}))
```

Questpie's derived surface per collection is the reference target:

| Artifact | Description |
|---|---|
| REST API | 5 typed routes/collection (list, get, create, update, delete) |
| Client SDK | typed methods with full response types |
| Admin | generated admin (`@questpie/admin`), schema-derived |
| Jobs | job infra aligned to collections |
| MCP | connect models to AI agents |

## What Kwiva Reimplements, Independently

Kwiva does **not** depend on `@questpie/*` (no imports, no peer deps, no runtime coupling). Instead it ships its own data foundation with the same architectural payoff:

| Questpie-derived artifact | Kwiva-owned equivalent |
|---|---|
| one-schema DSL (`@questpie/core`) | `@kwiva/schema` field DSL + `@kwiva/data` `defineModel` (function-based, per-model files — ADR-0018) |
| REST API derivation | generated model routes in `@kwiva/http` (deterministic 5-route shape) |
| Typed client | `@kwiva/client` typed RPC SDK (type-level, zero codegen) |
| Admin | Kwiva Studio (`@kwiva/studio`) generated screens |
| Jobs | `@kwiva/queue` `defineJob` with model-aligned payload typing |
| MCP connector | `@kwiva/mcp` from model/controller IR |
| Migrations/diff | `kwiva db:diff` / `db:migrate` (model IR → SQL steps) |
| OpenAPI | route manifest → OpenAPI 3.1 |

Full parity mapping lives in [07-feature-catalog §3a](../07-feature-catalog.md) (the "Questpie-derived feature set" table).

## Design Notes Inspired by Questpie (for our implementation)

1. **Collection-first ergonomics**: `fields((f) => ({...}))` builder gives per-field typing — Kwiva's field factory follows the same shape.
2. **Serially-derived outputs**: resolver → client → admin must generate from one IR (intermediate representation of the schema), not three ad-hoc generators — Kwiva's `src/.kwiva/model-ir.json` is that IR.
3. **Validation flows from the field types** — no separate validation copy.
4. **Bun-first dev** and Postgres-first prod (SQLite-compatible dev connector).
5. **Deterministic ordering**: 5 routes/collection is predictable; Kwiva keeps this shape so docs and tooling are uniform.

## Explicit Non-Goals (respecting independence)

- No import from `@questpie/*` anywhere in `@kwiva/*` or app code generated by Kwiva.
- No branding/derived-works products: none of Questpie's bundled products (e.g. Autopilot) are adopted.
- Kwiva's DSL differs where it improves Kwiva conventions (per-model files, tenancy field, audit fields, function-based form, policy integration).
