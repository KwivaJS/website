# AI & MCP (/docs/ai-mcp)



Kwiva can expose your application to AI agents as callable tools through the Model Context Protocol. The server, the tool list, and the input schemas are not written by hand — they are generated by `@kwiva/mcp` from the same model and controller IR that produces your database, REST API, and typed client. If you already have models, you already have an agent surface.

This reverses the usual integration work. There is no protocol glue to write, no tool registry to keep in sync, and no second schema that can drift from your application. `@kwiva/mcp` treats your existing app as the source of truth and renders an agent-facing surface from it.

## What the MCP Integration Provides [#what-the-mcp-integration-provides]

* **Generated tools from models** — every opted-in model becomes `list`, `get`, `create`, `update`, and `delete` tools with schemas derived from the model IR
* **Controller actions as tools** — custom controller actions are exposed as tools with their exact input and output types
* **Custom tools** — `defineMcpTool` for behavior that does not map to a route
* **The framework's security model, intact** — every tool call runs through policies, per-tool permissions, and tenant scoping
* **Auditable by default** — every tool call is a trace span plus a structured log entry
* **Two transports** — stdio for local development and agents, streamable HTTP for remote access

The combination is deliberately boring: an agent gets the same data, the same validation, the same permissions, and the same audit trail as every other caller. The MCP surface adds a channel; it does not add a new security model.

## How the IR Becomes AI-Callable Tools [#how-the-ir-becomes-ai-callable-tools]

The path from a model to an agent tool is the same derivation pipeline everything else uses:

```plaintext title="how-the-ir-becomes-ai-callable-tools.txt"
src/app/models/*.ts ──► model IR ──► @kwiva/mcp ──► agent-callable tools
src/app/http/controllers/*.ts ──► route manifest ──► controller actions as tools
```

Two sources feed the surface:

1. **Models.** Every model you opt in generates a deterministic family of tools. An `invoices` model yields `invoices_list`, `invoices_get`, `invoices_create`, `invoices_update`, and `invoices_delete`. Tool inputs are the same schemas the generated routes validate against — the agent's arguments pass through exactly the validation an HTTP body passes through.
2. **Controllers.** Custom actions on opted-in controllers become tools with the action's own typed input and output. A `reports` controller with a `summary` action yields a `reports_summary` tool. The inputs an API client would send to `GET /reports/summary` are the inputs the tool declares.

Enablement is one config module. Opt in the models and controllers you want to expose, choose a transport and an auth strategy, and set a read-only switch for your entire agent surface:

```ts title="src/config/mcp.ts"
// src/config/mcp.ts
import { defineConfig } from '@kwiva/config'

export default defineConfig('mcp', {
  defaults: {
    enabled: true,
    route: '/mcp',
    transport: 'http',                 // 'http' (streamable) | 'stdio'
    auth: 'bearer',                    // token strategy; session cookies also supported
    models: ['invoices', 'customers'], // generate tools for these models
    controllers: ['reports'],          // expose custom actions as tools
    readOnly: false,                   // true → list/get only
  },
})
```

The `models` list is an allowlist, not an all-or-nothing switch. Models and controllers you do not list stay out of the agent surface, and `readOnly: true` shrinks the whole surface to `list` and `get` regardless of what the routes allow. See [MCP Server](/docs/ai-mcp/mcp-server) for the full option table.

## What a Generated Tool List Looks Like [#what-a-generated-tool-list-looks-like]

For config with `models: ['invoices', 'customers']` and `controllers: ['reports']`, the agent discovers:

| Tool                                                                                          | Kind                                 |
| --------------------------------------------------------------------------------------------- | ------------------------------------ |
| `invoices_list`, `invoices_get`, `invoices_create`, `invoices_update`, `invoices_delete`      | Generated from the `invoices` model  |
| `customers_list`, `customers_get`, `customers_create`, `customers_update`, `customers_delete` | Generated from the `customers` model |
| `reports_summary`                                                                             | Controller action tool               |
| Any `defineMcpTool` exports                                                                   | Custom tools you author              |

Names are deterministic — `{model}_{action}` for model tools, `{controller}_{action}` for controller tools — so the surface is predictable to agents, documentation, and your own tooling. There is no separate convention to learn on the MCP side.

## Semantics at a Glance [#semantics-at-a-glance]

| Guarantee          | How it holds                                                                                                                      |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| Policy enforcement | Tools run through the same policies as your routes; the bearer token identifies a user or service principal whose abilities apply |
| Tenant scoping     | The token binds a tenant; cross-tenant access is impossible                                                                       |
| Validation         | Tool input schemas are the route schemas                                                                                          |
| Auditability       | Every tool call is a distributed trace span and a structured log entry                                                            |

Each guarantee is worth reading in full on the [Agent Integration](/docs/ai-mcp/agent-integration) page, because all of them follow from one fact: &#x2A;*tools are not an alternate code path.** A tool call invokes the same query builder, the same policy checks, and the same validation pipeline as the corresponding route.

## When to Use the MCP Surface [#when-to-use-the-mcp-surface]

The generated MCP server is the fastest way to give an AI agent first-party access to your application:

* **Internal operator agents** — an agent that drafts invoices, digests support tickets, or summarizes sales needs the real data, with the real permissions attached
* **Read-only research agents** — an analyst agent that explores your data needs `list`/`get` over every opted-in model, and the `readOnly` throttle makes that safe by construction
* **Action automation** — controller action tools let an agent trigger real, policy-approved operations with the session and tenant context of the calling identity

The surface is derived, so enabling it costs none of the maintenance an integration usually demands. Your existing models define both what the agent can do and how carefully it can do it.

## Where MCP Fits in the Framework [#where-mcp-fits-in-the-framework]

MCP is one more consumer of the model IR, sitting alongside the REST API, typed client, OpenAPI, and Studio. Because it is derived rather than duplicated, the agent surface can never reflect a stale schema. Kwiva exposes the data plane to agents; the agents bring their own models.
