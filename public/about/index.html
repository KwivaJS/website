About — Kwiva

A framework should make architecture feel obvious.

Kwiva exists because serious TypeScript applications deserve what mature ecosystems have: one coherent framework. This page is the reasoning — the philosophy, the boundaries and the decisions behind it.

v0.3 · active development/21 decision records/12 research notes

Building a serious application on the modern stack means assembling it yourself: runtime, router, HTTP layer, ORM, validation, auth, queues, realtime, SSR, observability, deployment.

Each choice is defensible. Together they are a tax — sixteen decisions and all the glue between them, before a single feature ships. The glue never disappears; it becomes the thing you maintain.

Kwiva's premise is that a framework should provide coherent defaults and abstractions — without preventing developers from extending the system. Batteries included, never batteries forced.

02Philosophy

Eight principles, each with a technical consequence.

Not mission statements — positions you can check against the code.

  1. 01

    Coherence over fragmentation

    One shape, one grammar, one narrative. The application talks to a framework, not to a dozen unaffiliated libraries.

    → app code imports only @kwiva/*

  2. 02

    Framework-owned APIs

    Kwiva owns the application-facing surface. Engines live sealed behind it, configured by the framework, never touched by app code.

    → no-engine-imports lint gate, enforced by oxlint

  3. 03

    Explicit over magical

    Plain, serializable definitions — no decorators, no classes, no config sprawl. What you read is what runs.

    → definitions you can read, diff and generate

  4. 04

    Convention through defineX

    Every construct is a factory with one grammar. The syntax you learn for models is the syntax you use for everything.

    → 17 factories · one grammar (ADR-0019)

  5. 05

    Type safety throughout

    The model IR drives types from database to API to client. End-to-end inference with zero runtime codegen.

    → typed RPC client, generated not hand-written

  6. 06

    Batteries included, not forced

    Sensible defaults everywhere — and every defineX accepts full inline configuration. When you override, inline wins.

    → escape hatches are the rule (ADR-0020)

  7. 07

    Production-first

    Stateless by construction, observability inside, queues and caching built in. Scaling is a deploy concern, not a rewrite.

    → multi-instance without re-architecture

  8. 08

    Runtime flexibility

    Bun primary, Node compatible, edge via presets. The runtime is a build target — not an identity.

    → one codebase · eight deploy targets

04Decisions

Why these choices.

Every major choice is recorded as an ADR — with context and consequences. These shape the framework most.

  1. ADR-0007Bun as the primary runtimeNative TypeScript, fast startup, single-binary output — with Node kept compatible.
  2. ADR-0002Nitro as the server foundationDeploy presets, storage, cache and tasks without leaking the engine into app code.
  3. ADR-0003A framework-owned HTTP APILifecycle, guards and macros designed in-house — Elysia is a reference, not a dependency.
  4. ADR-0004 · 0018The model layer as a function DSLdefineModel produces typed IR that derives the whole data plane.
  5. ADR-0006Kwiva owns SSRStreaming-first rendering is part of the framework, not a bolted-on adapter.
  6. ADR-0008 · 0021The oxc toolchain inside the CLIrolldown, oxlint, oxfmt — Rust-speed dev, check, build and format in one binary.
  7. ADR-0009Better Auth as the sealed auth engineSessions, OAuth and passkeys behind defineAuth — swappable, never imported.
  8. ADR-0015Tenancy-first data accessTenant isolation enforced in the data layer, not sprinkled through handlers.

05defineX

A language, not a collection of APIs.

Seventeen factories, one grammar. The convention is the product: reading app code should feel like reading a description of the product.

src/app/models/post.ts
export const Post = defineModel("posts", (f) => {
  id: f.id(),
  title: f.string(),
  status: f.enum("draft", "published"),
  author: f.belongsTo(() => User),
}, { timestamps: true });

No decorators. No classes. No registration files. A model is a value — which is why the framework can derive migrations, the REST API, the typed client, Studio, OpenAPI and MCP tools from it. The same grammar declares controllers, pages, jobs, policies and commands. Learn it once; it never changes shape.

09Direction

Where this is going.

Kwiva is at v0.3, in active development — built in phases, each with a verifiable milestone.

phase 1 — next

MVP kernel

The full defineX surface — HTTP lifecycle, router + SSR, data hooks, auth, tenancy, Studio v0, oxc integration, node + bun presets.

phase 2 — then

Realtime + ops

Events and channels, queue transports with DLQ, tasks and schedule, cache tags, OTel observability, Studio v1, MCP v0.

phase 3 — later

Ecosystem

Modules and first-party packages, upgrade codemods, edge hardening, dev overlay — toward the public 1.0.

explicitly out, v1

No visual drag-drop CMS. No hosted cloud. No native mobile. No non-TypeScript application languages. The scope is the framework.
